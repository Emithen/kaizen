## type

슬슬 여러 파일을 왔다갔다 하다보니까 전달되어야 하는 데이터들의 타입이 명시되지 않는 것이 불편해지기 시작했다.
인터페이스를 씌우기 위해서는 type 이 필요할 것 같다.

## 컴포넌트와 정보의 생애

컴포넌트의 생애, 그리고 정보의 생애
두 가지가 엇갈리니 꽤 헷갈린다.
상태 정보의 생애를 설계할 때에는 접근하는 이벤트와 그에 따른 액션도 전부 고려해야 한다.
이벤트는 보통 함수로 표현되므로 어떤 함수가 호출되었을 때 다른 어떤 함수를 이어서 실행할 것인지 논리적 연결이 존재하면 좋을 것 같다.
record 나 객체형 매퍼, 함수형 매퍼 등으로 선언하거나 아예 이벤트 액션 테이블을 만드는 것도 방법일지도.

## 영속화 결정

id 를 비영속화하기로 했다.
그 이유는 id 를 생성하기 위해서는 최소한 고유성을 지켜주어야 하는데 현재 id 를 발급하는 주체가 컴포넌트라 영속적인 규약을 제공할 수 없기 때문이다.
