## console.error(...)

아직 이게 왜 usePosts 계층에 있어야 하는지 명확한 이유를 구하지 못했다.
나중에 error 관리, 예외 처리, 분기적 화면 반응 등을 고려한 서비스 전체 구조를 완성시켜나가면서 어디에 존재하는 것이 디버깅이나 코드 직관성에 도움이 되는지 가늠해 볼 예정이다.


## Failed to fetch

이제 이 메시지는 console 에서만 확인할 수 있고 사용자가 보는 화면에 전달되지 않는다.
사용자/개발자 가 알아야할 정보를 영역을 구분하여 표시하기 시작했다.


## string -> boolean

Board 측에서 알아야할 정보 (actionError 의 발생 여부) 만을 담백하게 전달한다.
원래 message 운반 책임을 갖고 있었을 때에는 message 를 string 으로 들고 있었어야 했다.
그 경우 actionError 가 담고 있는 string 이 { error 발생 여부, 해당 error 의 message } 두 가지 상태 정보를 모두 보존해야 했다.
하나의 상태 변수가 여러 상태 정보를 동시에 들고 있게 될 경우 상태 관리가 복잡해지거나 비직관적으로 변모할 가능성이 있는 것 같아서 지금이 더 좋은 것 같다.
usePosts 에서는 error 의 분류를 api 로부터 전달받아서 유의미한 구분을 적용해 상태 정보로 저장, Board 는 사용자 화면에 노출시킬 메시지를 들고 있다가 usePosts 로부터 error 발생여부를 전달 받아서 분기적으로 화면 갱신 -> 이렇게 책임을 나눠 갖는게 직관적이고 읽기 쉬운 코드인 것 같다.


## 현재 구조 정리

경계 / 정책 / 표현 - 3계층 구조
경계: 실패의 종류를 반환 (throw 가 아닌 return)
정책: 유의미하게 구분되는 화면 반응 단위로 error 상태를 구분 관리, 표현층에게 직관적인 인터페이스 제공
표현: 제공받은 인터페이스의 플래그나 정보를 활용해 적절한 분기 및 화면 반응 구성


## 현재 구조의 한계점들

- error slot 이 서로 다른 유의미한 화면 반응의 수만큼 존재해야 한다.
    -> useReducer 나 상태 묶기를 통해 해결
- actionError: boolean 은 삭제와 생성을 모두 관리하기 때문에 둘 중 어떤 이벤트에 의한 오류인지는 호출부에서 구분할 수 없다.
    -> kind 판별자(?)
- loadError 는 현재 구조가 추구하는 방향과 어긋나 있다.
    -> loadError 도 boolean 으로 변경, usePosts 정책 계층에서 소멸하는 message 정보를 console.error 로 개발자 전용 채널에 표시
